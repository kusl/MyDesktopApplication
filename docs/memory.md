Purpose & context
Kushal is developing MyDesktopApplication, a cross-platform country quiz game built with .NET 10 and Avalonia UI, targeting desktop (Windows, Linux, macOS with x64/ARM64 variants) and Android platforms. The application challenges users to compare countries across various metrics like population, GDP, area, and other statistics. The project follows Clean Architecture principles with separate Core, Infrastructure, Shared, and platform-specific projects, using Entity Framework Core with SQLite for data persistence and implementing MVVM patterns with CommunityToolkit.Mvvm.
Kushal maintains a "One Team, One Build" philosophy, preferring unified solutions where all team members experience the same build process rather than creating platform-specific silos. He emphasizes using only completely free, open-source dependencies (MIT, Apache-2.0, BSD, or Public Domain licensed) and explicitly avoids packages with commercial licensing restrictions. The project uses modern .NET technologies including SLNX solution format and Central Package Management.
Current state
The application is actively deployed via GitHub releases with automated CI/CD pipelines, distributed to Android devices through Obtainium. Recent development has focused on resolving complex build system issues, particularly Android-specific problems like aapt2 daemon deadlocks and resource compilation hangs. The project has evolved from basic compilation errors to sophisticated deployment challenges including APK signing, GitHub Actions workflow optimization, and cross-platform compatibility.
Current technical stack includes Entity Framework Core for data persistence, comprehensive test coverage with unit and integration tests, and automated versioning using GitHub run numbers. The application features 80+ countries with real statistical data across 8 question categories, persistent game state tracking, and responsive UI design optimized for various screen sizes from Android phones to large tablets.
Key learnings & principles
Kushal has identified that Android builds in .NET can suffer from aapt2 daemon deadlocks, requiring specific MSBuild properties like AndroidUseAapt2Daemon=false to prevent infinite hangs. GitHub Actions workflows need careful separation between desktop-only CI builds and full platform builds that include Android workload installation to avoid unnecessary complexity and build failures.
Version management for Android requires strict incrementing of ApplicationVersion (versionCode) between builds for proper app updates - static version codes prevent in-place updates and force users to uninstall/reinstall. Cross-framework dependency issues arise when projects target different frameworks (net10.0 vs net10.0-android), requiring explicit PackageReferences rather than relying on transitive dependencies.
The importance of surgical fixes over comprehensive rewrites has been demonstrated multiple times - minimal, targeted changes preserve existing functionality while comprehensive file overwrites often introduce new XAML binding errors and break working features.
Approach & patterns
Kushal strongly prefers automation through comprehensive shell scripts rather than manual file editing, consistently requesting "one-liner" commands and executable solutions. His development workflow emphasizes systematic debugging using process monitoring tools, ADB logging for Android issues, and iterative problem-solving that addresses root causes rather than symptoms.
The project uses conditional build logic to handle different deployment scenarios - signed APKs for production releases and unsigned builds for development/testing. GitHub secrets management enables secure keystore handling while maintaining fallback logic for pull requests from forks using dummy keystores for validation.
Problem-solving follows a pattern of identifying specific error messages, using project knowledge search to understand current implementations, then creating targeted fixes that maintain architectural consistency. Build processes include comprehensive cleanup of stuck processes, artifact cleaning, and verification steps to ensure solutions work correctly.
Tools & resources
Development environment is Fedora Linux with proper Java JDK configuration (preferring JDK 21/17/11 over newer versions for Android compatibility). Android development uses official Google SDK command-line tools rather than distribution packages. GitHub Actions workflows use latest action versions (checkout@v6, setup-dotnet@v5, setup-java@v5 with Temurin distribution).
The project leverages Entity Framework Core with design-time factories for migrations, NSubstitute and Shouldly for testing (replacing commercial alternatives), and comprehensive CI/CD pipelines with separate workflows for continuous integration, development builds, and production releases. Deployment uses GitHub releases with automatic asset generation and Obtainium for Android distribution.
On the horizon
Future considerations include maintaining compatibility with evolving .NET Android workloads, optimizing build performance as the project scales, and ensuring the unified solution approach continues to work effectively as new platform targets are potentially added. The project architecture is positioned to handle additional question types and country data expansion while maintaining the responsive, cross-platform user experience.
